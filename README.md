# KhadSan AI : ตรวจความสดผลไม้ด้วย AI

โครงงาน **ระบบตรวจระดับความสดและคัดเกรดผักผลไม้อัตโนมัติด้วยดีปเลิร์นนิง**
(Automated Fruit and Vegetable Quality and Freshness Classifier)

ถ่ายรูปหรืออัปโหลดรูปผลไม้เข้าเว็บ ในรูปจะมีกี่ลูกก็ได้ เว็บจะตีกรอบให้ทุกลูก บอกว่าเป็นผลไม้อะไร สดหรือเน่า มั่นใจกี่ % แล้วสรุปให้ว่าลูกไหนต้องคัดออก
ตอนนี้รองรับ 5 ชนิด คือ แอปเปิล กล้วย ส้ม ทับทิม มะนาว

> ทำเพื่อการศึกษา ใช้เป็นตัวช่วยคัดแยกเบื้องต้นเท่านั้น ไม่ได้ใช้รับรองคุณภาพหรือความปลอดภัยของอาหาร

**ปัญหาที่อยากแก้:** ผู้ประกอบการคัดบรรจุผลไม้ขนาดเล็ก (กลุ่มเกษตรกร วิสาหกิจชุมชน โรงคัดบรรจุ) ยังใช้คนหยิบดูทีละลูก
ปัญหาไม่ได้อยู่ที่ดูไม่ออก แต่อยู่ที่ไม่รู้ว่าแต่ละล็อตเน่ากี่ % แต่ละคนแต่ละรอบคัดไม่เท่ากัน และไม่มีหลักฐานไว้ต่อรองกับผู้ส่งหรือผู้ซื้อ
ระบบนี้ตรวจได้ทีละหลายลูกจากรูปเดียว สรุปว่าต้องคัดออกกี่ลูก (เน่ากี่ %) ลูกเลขไหน และให้คนตัดสินใจขั้นสุดท้ายเสมอ


## ทีมและหน้าที่

ทุกคนช่วยกันหารูปผลไม้และช่วยกันเทรนโมเดล

- **ฟิว** นายชินวัตร อ่วมแก้ว (ML Engineer) : เทรน YOLOv8n เตรียมและแบ่งข้อมูล ทดลองปรับแต่งโมเดล วัดผล แล้วเซฟโมเดลตัวที่ดีที่สุด
- **หยก** นางสาวศรีรัตน์ อินทลัย (MLOps & Frontend) : ทำเว็บ Flask ทั้งอัปโหลด กล้อง และสแกนสด เอาโมเดลมาต่อกับเว็บ เตรียมโน้ตบุ๊ก Colab ดูแล GitHub และ README
- **นีโอ** นายเดชาธร หุ้มไธสง (Data Quality & Model QA) : ตรวจคุณภาพรูป วิเคราะห์ Confusion Matrix ลองใช้เว็บหาบั๊กทั้งบนคอมและมือถือ และคิดตัวเลขผลกระทบทางธุรกิจ
- **เมษา** นางสาวบุญพิทักษ์ โรจนประภาวสุ (Documentation) : เขียน Final Report ใน Word ไม่เกิน 5 หน้า เน้นหมวด Model Tuning & Optimization 
- **ใบหม่อน** นางสาวนิชาภา ศรีแจ่มใส (Presentation) : ทำสไลด์ Canva สำหรับนำเสนอ 10-15 นาที 


## ระบบทำงานยังไง

```

      │
      ▼
เว็บ Flask (web/app.py) ── เช็กไฟล์ (jpg/png/webp ≤ 10 MB) ── หมุนรูปให้ตรง ── พื้นโปร่งใสเป็นขาว
      │
      ▼
โมเดล YOLOv8n (web/models/best_detect.pt) ── ตีกรอบ + บอกคลาส เช่น Orange_Bad

      ▼
```

- โมเดลเป็น **YOLOv8n** (Object Detection) ของ Ultralytics ทีมเอามา fine-tune เองบน Google Colab
- มี 10 คลาส คือ 5 ชนิด × Good (สด) / Bad (เน่า)
- เว็บเขียนด้วย Python **Flask** + HTML/CSS + JavaScript ที่ทีมเขียนเอง ถ้าปิด JavaScript ก็ยังอัปโหลดรูปตรวจได้


## ข้อมูลที่ใช้

**ชุดเทรนคือ Fruits Quality จาก Roboflow Universe** มีกรอบรอบผลไม้แต่ละลูกพร้อมป้าย Good / Bad
เราเก็บไว้แค่ 5 ชนิด ตัดฝรั่งกับคลาสที่ป้ายแปลกๆ ออก เหลือ 2,320 รูป
รูปที่หน้าตาเกือบเหมือนกัน (ถ่ายลูกเดิมหลายช็อต) เราจับไว้กลุ่มเดียวกันก่อน แล้วค่อยแบ่ง train / val / test เป็น 70 / 15 / 15
ที่ทำแบบนี้เพราะไม่อยากให้รูปคล้ายกันไปโผล่ทั้งใน train และ test (กัน data leakage) คะแนน test จะได้ไม่ดูดีเกินจริง

**ชุดทดสอบภายนอกคือ Fruit and Vegetable Diseases Dataset จาก Kaggle** เป็นรูปจากแหล่งอื่นที่โมเดลไม่เคยเห็น เอาไว้ดูว่าโมเดลใช้กับรูปจริงนอกชุดเทรนได้แค่ไหน
ชุดนี้มีแค่แอปเปิล กล้วย ส้ม และไม่มีกรอบ เลยใช้ชื่อโฟลเดอร์เป็นคำตอบ คัดมาคลาสละ 100 รูป ไม่เอารูปซ้ำ รวม 600 รูป


## การทดลองปรับแต่งโมเดล (Model Tuning)

ตัวตั้งต้น (baseline) คือ yolov8n ที่เทรนกับ COCO มาแล้ว ใช้ SGD, learning rate 0.01 คงที่, batch 16, weight decay 0.0005
แต่ละการทดลองเปลี่ยนจาก baseline ทีละอย่าง จะได้รู้ว่าผลที่ต่างไปมาจากอะไร

- `1_scratch_sgd` เทรนจากศูนย์ ไม่ใช้โมเดลที่เทรนมาแล้ว
- `2_pretrained_sgd` คือ baseline
- `3_adam` เปลี่ยน optimizer เป็น Adam
- `4_rmsprop` เปลี่ยน optimizer เป็น RMSProp
- `5_cosine_lr` ให้ learning rate ค่อยๆ ลดแบบ Cosine
- `6_batch32` ใช้ batch size 32
- `7_no_weight_decay` ไม่ใช้ L2 (weight decay)

ทุกการทดลองใช้ **Early Stopping** ถ้าคะแนน validation ไม่ดีขึ้น 10 รอบติดก็หยุด เทรนสูงสุด 60 รอบ รูปขนาด 640×640
เราเลือกตัวที่ดีที่สุดจาก **mAP50 บน validation** แล้วค่อยเอาไปวัดผลจริงบน **test** (Precision, Recall, F1, mAP50, Confusion Matrix) และบนชุดทดสอบภายนอก

ข้อควรรู้มี 2 อย่าง
- Early Stopping ของ YOLO ดูคะแนน mAP ไม่ได้ดู Validation Loss ตรงๆ แต่เราก็เก็บกราฟ Loss ไว้ดูด้วย
- YOLO detect ไม่มี Dropout ให้ปรับ เราเลยใช้ L2 เป็นตัวทดลองด้าน Regularization แทน ส่วน BatchNorm มีอยู่ในโมเดลอยู่แล้ว

**ผลรอบ 1** วัดบน test set 348 รูป (ผลไม้ 1,055 ลูก) ที่โมเดลไม่เคยเห็นตอนเทรน
คอลัมน์ "รูปแหล่งอื่น" คือทายถูกทั้งชนิดและสด/เน่า บนรูป Kaggle 600 รูป

| การทดลอง | หยุดที่ epoch | Val mAP50 | Test Precision | Test Recall | Test F1 | Test mAP50 | รูปแหล่งอื่น |
|---|---|---|---|---|---|---|---|
| 1_scratch_sgd | 54 | 0.946 | 0.891 | 0.893 | 0.892 | 0.942 | 50.2% |
| 2_pretrained_sgd | 46 | 0.960 | 0.904 | 0.911 | 0.907 | 0.952 | 53.2% |
| 3_adam | 60 | 0.967 | 0.914 | 0.918 | 0.916 | 0.952 | 53.2% |
| 4_rmsprop | 32 | 0.318 | 0.307 | 0.442 | 0.362 | 0.291 | 0.3% |
| **5_cosine_lr (ดีสุดของรอบ 1)** | 60 | **0.975** | **0.941** | **0.964** | **0.953** | **0.970** | **60.0%** |
| 6_batch32 | 59 | 0.960 | 0.923 | 0.929 | 0.926 | 0.962 | 51.7% |
| 7_no_weight_decay | 53 | 0.965 | 0.905 | 0.930 | 0.917 | 0.953 | 54.0% |

สรุปผลรอบ 1
- ตัวที่ดีที่สุดคือ `5_cosine_lr` ได้ **F1 0.953** ผ่านเป้า F1 ≥ 0.85 ที่ตั้งไว้ใน Proposal และทายรูปจากแหล่งอื่นได้ดีที่สุดด้วย
- learning rate แบบ Cosine ได้ผลดีที่สุด ส่วนเทรนจากศูนย์ได้คะแนนต่ำสุดในกลุ่มที่เทรนได้ปกติ ทั้งบน test และรูปจากแหล่งอื่น
- RMSProp เทรนไม่นิ่ง loss พุ่งสูงตั้งแต่รอบแรก คะแนนแกว่งตลอด และหยุดเร็วที่ epoch 32
- การทดลอง 2, 3, 6, 7 ได้ F1 อยู่ระหว่าง 0.907-0.926 และแต่ละการทดลองรันแค่ครั้งเดียว เลยยังสรุปไม่ได้ว่า Adam, batch 32 หรือการไม่ใช้ weight decay ดีกว่า baseline จริง
- ถ้าดูรายคลาส ตัวที่แย่สุดคือส้มเน่า (F1 0.908) ใน 65 ลูก โดนทายเป็นส้มสด 3 ลูก และมะนาวเน่า 3 ลูก ส่วนมะนาวสดกับมะนาวเน่าก็ยังสลับกันอยู่บ้าง (18 ลูกจาก 313 ลูก)

**ลองกับรูปจากแหล่งอื่น (Kaggle 600 รูป ที่โมเดลไม่เคยเห็น)** `5_cosine_lr` ทายถูกทั้งชนิดและสด/เน่า 60.0% ทายชนิดถูก 79.2% ทายสด/เน่าถูก 73.3%
ต่ำกว่า test set เยอะ เพราะรูปจากแหล่งอื่นถ่ายคนละแบบ (พื้นขาว รูปสตูดิโอ) กับรูปที่ใช้เทรน
กล้วยทายได้ดี (88-89%) ส้มสดได้ 80% แต่**ส้มเน่าแทบทายไม่ได้เลย (3%)** ส่วนใหญ่โดนทายเป็นส้มสด และแอปเปิลถูกราวครึ่งเดียว
แปลว่าต้องเพิ่มรูปเทรนให้หลากหลายกว่านี้ เลยเป็นที่มาของรอบ 2

**รอบ 2 : เพิ่มรูปเข้าชุดเทรน และแก้ RMSProp**

สิ่งที่ทำ
- เพิ่มรูป Kaggle 3,000 รูป (แอปเปิล กล้วย ส้ม ชนิดละสด 500 เน่า 500) ที่**ไม่ซ้ำกับชุดทดสอบภายนอก** เข้าไปในชุดเทรน
- รูป Kaggle ไม่มีกรอบ เราเลยให้โมเดลรอบแรกช่วยตีกรอบ แล้วใช้ชื่อโฟลเดอร์เป็นคำตอบสด/เน่า
  เก็บไว้เฉพาะกรอบที่โมเดลเห็นเป็นผลไม้ชนิดเดียวกับชื่อโฟลเดอร์ และกรอบต้องใหญ่พอ สุ่มดูด้วยตาแล้วกรอบถูกราว 95%
- ใส่**รูปพื้นหลังที่ไม่มีผลไม้** 126 รูปจาก COCO128 (คน ของใช้ รถ สัตว์) แบบไม่มีกรอบ
  เพราะรอบแรกโมเดลไม่เคยเห็นรูปที่ไม่มีผลไม้เลย ตอนลองกับกล้องเลยตีกรอบหน้าคนว่าเป็นทับทิม (มั่นใจราว 32%)
- ลองแก้ RMSProp ที่เทรนไม่นิ่ง โดยลด learning rate ลง 10 เท่า
- val กับ test ใช้ชุดเดิมของรอบ 1 ทุกตัว คะแนนเลยเทียบกันได้ตรงๆ

| การทดลอง | หยุดที่ epoch | Val mAP50 | Test Precision | Test Recall | Test F1 | Test mAP50 | รูปแหล่งอื่น |
|---|---|---|---|---|---|---|---|
| 4_rmsprop (lr 0.001) | 32 | 0.318 | 0.307 | 0.442 | 0.362 | 0.291 | 0.3% |
| 5_cosine_lr (ข้อมูลเดิม) | 60 | 0.975 | 0.941 | 0.964 | 0.953 | 0.970 | 60.0% |
| **8_cosine_more_data (ใช้ในเว็บตอนรอบ 2)** | 60 | 0.973 | 0.946 | 0.942 | 0.944 | 0.969 | **97.7%** |
| 9_rmsprop_low_lr (lr 0.0001) | 38 | 0.673 | 0.563 | 0.669 | 0.612 | 0.666 | 30.2% |

สรุปผลรอบ 2
- 4 กับ 5 เทรนซ้ำแล้วได้คะแนนเท่ารอบ 1 ทุกตัวเลข แปลว่าการเทรนของเราทำซ้ำได้ผลเดิม
- **เพิ่มรูป (8) ทำให้รูปจากแหล่งอื่นทายถูกจาก 60.0% เป็น 97.7%** ส้มเน่าจาก 3% เป็น 95% แอปเปิลจากราวครึ่งเป็น 97-98%
- แต่ต้องระวัง : รูปที่เพิ่มมาจาก Kaggle ชุดเดียวกับชุดทดสอบภายนอก (คนละรูป และกันรูปคล้ายกันออกแล้ว) ถ่ายสไตล์เดียวกันคือพื้นขาวแบบสตูดิโอ
  ตัวเลข 97.7% เลยบอกว่าโมเดลเก่งขึ้นกับรูปแบบนั้น ยังบอกไม่ได้ว่าเก่งกับรูปทุกแบบ
- บน test (รูปชุด Fruits Quality) 8 ได้ F1 0.944 ต่ำกว่า 5 อยู่ 0.009 ต่างกันไม่ถึง 1 จุด ถือว่าใกล้เคียงกัน
  แต่ส้มเน่าใน test แย่ลง (F1 0.908 เป็น 0.859) ใน 65 ลูก โดนทายเป็นส้มสด 5 ลูก มะนาวเน่า 6 ลูก
- ทั้ง 5 และ 8 ไม่ตีกรอบรูปคนกับรูปรถบัสแล้ว (ความมั่นใจขั้นต่ำ 0.40 เท่าเว็บ)
- RMSProp ลด learning rate แล้วดีขึ้น (F1 0.362 เป็น 0.612) แต่ยังห่างจาก SGD มาก

**ทำไมตอนรอบ 2 เว็บใช้ 8 ทั้งที่ Val mAP50 ต่ำกว่า 5 นิดเดียว (0.973 กับ 0.975)** (ตอนนี้เปลี่ยนเป็น 11 แล้ว ดูรอบ 3)
โค้ดเทรนเลือกตัวที่ Val mAP50 สูงสุดให้อัตโนมัติ ซึ่งได้ 5 แต่ทีมเลือก 8 เอง เพราะคะแนน test ห่างกันไม่ถึง 1 จุด
ส่วนรูปจากแหล่งอื่นห่างกันเกือบ 38 จุด และลูกเน่าที่ถูกทายว่าสดบนรูป Kaggle ลดจาก 75 รูปเหลือ 2 รูป ตอนเดโมใช้รูปถ่ายจริงที่หลากหลาย จึงเลือกตัวที่เคยเห็นรูปหลายแบบกว่า

ฝั่งเว็บใช้ความมั่นใจขั้นต่ำ 0.40 (เดิม 0.25) วัดบน test กับโมเดล 8 แล้ว เจอผลไม้น้อยลงแค่ 4 จาก 1,055 ลูก แต่ตัดกรอบมั่วๆ ที่มั่นใจต่ำออกได้

**รอบ 3 : ผลเชื่อได้แค่ไหน (เพิ่มส้มเน่า + เทรนซ้ำ 3 seed + ข้อสอบใหม่)**

รอบ 2 ยังตอบไม่ได้ 3 เรื่อง คือ ส้มเน่าแย่ลง / เทรนแบบละครั้งเดียว ไม่รู้ว่าคะแนนแกว่งแค่ไหน / ชุดแหล่งอื่นมาจากที่เดียวกับรูปที่เพิ่มเทรน และไม่มีมะนาว ทับทิม

สิ่งที่ทำ
- เพิ่มส้มเน่า 174 รูปจาก Roboflow `rotten-orange` เข้าชุดเทรน (ตัดรูปที่คล้าย val / test / ชุดทดสอบภายนอกออกแล้ว)
- เทรนค่าเดียวกับ 8 สามครั้ง ด้วย seed 42 / 2 / 3 (การทดลอง 10, 11, 12) รอบ 1-2 ล็อก seed 42 ไว้ เลยไม่เคยรู้ว่าผลแกว่งแค่ไหน
- ข้อสอบใหม่ที่มีกรอบทุกลูก ไม่เคยใช้เทรน
  - `new_test` (ข้อสอบอิสระ) : ทับทิมสด 150 รูป จาก Roboflow `quality-detection`
  - `same_source_test` (ดูประกอบ **ไม่ใช่ข้อสอบอิสระ**) : มะนาวสด/เน่า 298 รูป (`lime-quality`) + ทับทิมสด/เน่า 72 รูป (`pomegranate-aws5r`)
    ตอนตรวจเจอว่า 2 ชุดนี้มาจากชุดถ่ายเดียวกับ Fruits Quality (มีรูปเดียวกันเป๊ะ แค่เปลี่ยนชื่อไฟล์) ตัดรูปซ้ำออกแล้วแต่ยังนับเป็นแหล่งเดียวกัน

## วิธีใช้เว็บ

เอารูปเข้าเว็บได้ 3 แบบ
- **เลือกรูปจากเครื่อง** (บนคอมลากรูปมาวาง หรือก๊อปรูปแล้วกด Ctrl+V / ⌘V ก็ได้) แล้วกด **ตรวจเลย**
- กด **เปิดกล้อง** แล้ว**ถ่าย** แล้วกด **ตรวจเลย** แบบนี้จะได้ผลละเอียดทีละลูก
- กด **เปิดกล้อง** แล้วเลือก **สแกนสด** เล็งกล้องค้างไว้ กรอบสด/เน่าจะขึ้นบนภาพสดเลย ได้ราว 4-5 ภาพต่อวินาทีบนโน้ตบุ๊ก (ขึ้นกับเครื่องและเน็ต) เหมาะกับดูเร็วๆ แต่ไม่มีรายการละเอียด

ก่อนกดตรวจ ใส่ **"ในถาดมีกี่ลูก?"** ได้ (ไม่บังคับ) เว็บจะเทียบกับจำนวนกรอบ ช่องนี้ไม่ได้ช่วยให้ AI หาเจอเพิ่ม แต่ทำให้รู้ว่า AI ตรวจครบไหม
- ตีกรอบไม่ครบ : ตรา "ตรวจไม่ครบ N ลูก" (สีอิฐ เส้นคู่) และในป้ายบอกว่ากี่ลูกที่ AI ไม่ได้ตรวจ ให้คนตรวจเอง
- ตีกรอบเกิน : ตรา "กรอบเกิน N กรอบ" (อาจตีกรอบซ้อนลูกเดียวกัน)
- ตรงกันและสดทุกลูก : ตรา "สด N/N ลูก"
- ไม่ใส่ : ตราสดขึ้นแค่ "สด N ลูก" (ไม่รู้ว่ามีลูกที่ AI ไม่ได้ตีกรอบไหม) และใต้ป้ายเตือนสั้นๆ ว่าลูกที่ไม่มีกรอบ AI ไม่ได้ตรวจ

ตรา "คัดออก" บอก % เน่าของลูกที่ตีกรอบได้ด้วย เช่น "คัดออก 4 ลูก (50%)" ไว้เทียบแต่ละล็อต
หน้าผลตรวจขึ้นรูปก่อน (มือถือ) / รูปอยู่ซ้าย ป้ายอยู่ขวา (คอม) **แตะเลขในป้ายหรือในรายการ รูปจะเลื่อนมาและไฮไลต์ลูกนั้น** ไม่ต้องไล่หาเลขเอง บนมือถือมีปุ่ม **สแกนถาดต่อไป** ติดล่างจอ กดแล้วเลือก/ถ่ายรูปถาดใหม่ได้เลย
หน้าผลตรวจจะมีรูปที่ตีกรอบทุกลูกพร้อมเลขกำกับ มีป้ายตรวจคุณภาพบอกว่า AI ตีกรอบได้กี่ลูก (จากกี่ลูก ถ้าใส่จำนวนไว้) ลูกเลขไหนต้องคัดออก ลูกเลขไหนให้ตรวจซ้ำ และสดกี่ลูก
ถ้าไม่เจอผลไม้เลย ใต้ป้ายจะบอกวิธีถ่ายใหม่พร้อมปุ่มถ่ายใหม่
ข้างล่างเป็นรายการทีละลูก บอกชนิด สถานะ % ความมั่นใจ และสิ่งที่อาจทำให้ AI มั่นใจน้อยลง (เช่น ซ้อนกับลูกอื่น) ลูกเน่าขึ้นก่อน (แสดงไม่เกิน 30 ลูก)
เลขกำกับเรียงทีละแถว บนลงล่าง ซ้ายไปขวา เหมือนอ่านหนังสือ ความหนาเส้นกรอบและขนาดเลขโตตามขนาดลูก (ลูกเล็กเส้นบางเลขเล็ก มีขั้นต่ำ/ขั้นสูง) จะได้ไม่บังผลไม้ในรูปที่มีหลายลูก
รูปที่ผลไม้เยอะ กด "ดูรูปขนาดเต็ม (ซูมได้)" ใต้รูป (หรือแตะที่รูป) จะเปิดรูปในแท็บใหม่ ซูมดูเลขได้ และถ้าคัดออกหรือให้ตรวจซ้ำเกิน 6 ลูก ป้ายจะบอกแค่จำนวน ให้ไปดูเลขในรายการทีละลูก

แต่ละลูกได้ 1 ใน 3 ผล ตัดสินจากความมั่นใจของโมเดล (ค่าพวกนี้ตั้งไว้ใน `web/app.py`)
% ความมั่นใจ คือ AI แน่ใจในคำตอบของตัวเองแค่ไหน ไม่ได้แปลว่าสดกี่ %
- **สด** : ทายว่าสด และมั่นใจตั้งแต่ 70% (`HIGH_CONF`) กรอบเขียวเส้นทึบ
- **ให้ตรวจซ้ำ** : ทายว่าสด แต่มั่นใจ 40-69% กรอบเขียวเส้นประ ตรวจซ้ำก่อนส่ง เพราะลูกที่บอกว่าสดแต่จริงๆ เน่า คือลูกที่จะหลุดไปถึงลูกค้า
- **คัดออก** : ทายว่าเน่า มั่นใจตั้งแต่ 40% (`CONF_MIN` ทุกกรอบที่ตีได้) กรอบสีอิฐ คัดออกไว้ก่อน ดีกว่าปล่อยลูกเน่าหลุด
- ต่ำกว่า 40% ไม่นับว่าเจอผลไม้ ไม่ตีกรอบ (`CONF_MIN`)

ตราปั๊มกับข้อความ "ให้ตรวจซ้ำ" ใช้สีเหลืองอำพัน (มีงานต้องทำ) แต่กรอบในรูปยังเป็นเขียวเส้นประ (AI เอนไปทางสด) · เหตุผลของลูกที่ให้ตรวจซ้ำบอกครั้งเดียวใต้หัว "ทีละลูก"
ลูกสดและลูกที่ให้ตรวจซ้ำใช้ป้ายเลขพื้นขาว ลูกที่คัดออกใช้ป้ายเลขพื้นทึบ และลูกที่ให้ตรวจซ้ำใช้กรอบเส้นประ คนที่แยกสีไม่ออกก็ยังดูออก
ถ้าผลไม้ลูกเดียวกันโดนตีกรอบซ้อนกันหลายชนิด เว็บจะเก็บไว้กรอบเดียว ตัวเลขนับจะได้ไม่เกินจริง

ถ่ายให้เห็นผลไม้ทั้งลูกและแสงพอ ถ้าเป็นผลไม้ชนิดอื่นนอก 5 ชนิดนี้ โมเดลอาจทายผิดได้
กล้องเปิดได้เฉพาะเว็บที่เป็น HTTPS หรือ localhost (เป็นกฎของเบราว์เซอร์)

- ไม่เก็บรูปของผู้ใช้ไว้ในเซิร์ฟเวอร์ รูปถูกแปลงเป็นข้อความเพื่อแสดงในหน้าเว็บอย่างเดียว
- ภาพจากกล้องไม่ถูกส่งไปไหน จนกว่าผู้ใช้จะกดตรวจหรือกดสแกนสด ตอนสแกนสดจะส่งภาพย่อไปตรวจทีละภาพ และไม่เก็บรูป
- ถ้าไฟล์เสียหรือโมเดลพัง เว็บจะแจ้งเป็นภาษาไทย ไม่โชว์ข้อความ error ดิบของระบบ
- JavaScript ทีมเขียนเอง ไม่ได้ดึงโค้ดจากเว็บอื่น


## เครดิตและลิขสิทธิ์

**ข้อมูล**
- Fruits Quality Dataset โดยผู้ใช้ Roboflow `alex-day-qzfwa` (project `fruits-quality-qtdtf` version 1)
  https://universe.roboflow.com/alex-day-qzfwa/fruits-quality-qtdtf : สัญญาอนุญาต **CC BY 4.0**
- Fruit and Vegetable Disease (Healthy vs Rotten) โดย `muhammad0subhan` บน Kaggle
  https://www.kaggle.com/datasets/muhammad0subhan/fruit-and-vegetable-disease-healthy-vs-rotten : ดูเงื่อนไขการใช้งานในหน้า Kaggle
- COCO128 (รูปตัวอย่าง 128 รูปจาก COCO 2017 ของ Ultralytics) ใช้เป็นรูปพื้นหลังที่ไม่มีผลไม้ : https://cocodataset.org (ใช้ภาพตามเงื่อนไข COCO Terms of Use)
- รอบ 3 จาก Roboflow Universe ทั้งหมดสัญญาอนุญาต **CC BY 4.0**
  - rotten-orange (version 5) โดย `trns-workspace-wydhc` : https://universe.roboflow.com/trns-workspace-wydhc/rotten-orange-dvh3t (รูปเทรนเพิ่ม)
  - quality-detection (version 1) โดย `sliit-b09eh` : https://universe.roboflow.com/sliit-b09eh/quality-detection-yy0x3 (ข้อสอบ new_test)
  - lime-quality (version 1) โดย `yasmines-workspace-whz7y` : https://universe.roboflow.com/yasmines-workspace-whz7y/lime-quality (ข้อสอบ same_source_test)
  - pomegranate-aws5r (version 1) โดย `curry` : https://universe.roboflow.com/curry/pomegranate-aws5r (ข้อสอบ same_source_test)
- ชุดรูปที่ทีมรวบรวมเพิ่ม (Team-collected set) : รูปจากเว็บและภาพสต็อก ใช้วัดผลภายในเท่านั้น ไม่ได้อัปขึ้น GitHub

**ซอฟต์แวร์**
- [Ultralytics YOLOv8](https://github.com/ultralytics/ultralytics) ใช้สัญญาอนุญาต **AGPL-3.0**
  ถ้าเอาโปรแกรมที่ใช้ YOLOv8 ไปเปิดให้คนอื่นใช้ (รวมถึงเปิดเป็นเว็บ) ต้องเปิดเผยซอร์สโค้ดด้วย repo นี้จึงเปิดเป็นสาธารณะ
- Flask, Pillow, PyTorch ใช้ตามสัญญาอนุญาตของแต่ละโปรเจกต์
